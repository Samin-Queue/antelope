# 기술 검토 — 진행 시각화와 개입

요청 6건을 「지금 되는 것 · 배선이 필요한 것 · 실행 구조를 바꿔야 하는 것」으로
가른다. 순서는 그 난이도 순이 아니라 **앞의 것이 없으면 뒤가 거짓이 되는** 순이다.

---

## 요약

| #   | 요청                       | 판정            | 이유                                                                  |
| --- | -------------------------- | --------------- | --------------------------------------------------------------------- |
| 1   | 4×2 그리드 · 카드별 라이브 | **가능**        | 이벤트에 `stage` 한 필드만 더하면 된다                                |
| 2   | 활성 카드 보라 테두리      | **가능**        | 이미 `stage:start/done` 이 온다                                       |
| 3   | 동시 n개 점등              | **부분**        | 파이프라인이 **완전 직렬**이라 켤 것이 없다. 병렬화가 먼저다          |
| 4   | 되돌아가는 티키타카        | **아직 없다**   | 에이전트끼리 되부르는 루프가 코드에 없다. UI 만 만들면 보여줄 게 없다 |
| 5   | 브라우저 화면을 카드에     | **가능**        | `ApplyEvent.frame` 이 이미 JPEG 을 흘린다                             |
| 6   | 입력을 큰 다이얼로그로     | **가능**        | `NeedsForm` 을 `Dialog` 로 옮기면 된다                                |
| 7   | 중간 개입(명령 전달)       | **둘로 갈라야** | 주입은 가능, **재계획은 오케스트레이션을 바꿔야 한다**                |

**가장 중요한 판단 하나** — 3·4번을 위해 **가짜로 불을 켜면 안 된다.**
이 제품이 파는 것은 「추측하지 않는다」이고, 진행 표시가 실제와 다르면 그 주장이
화면에서 먼저 무너진다. 켤 것이 없으면 켜지 않고, 병렬·왕복을 **실제로 만든 뒤**
켠다.

---

## 1. 지금 구조

```
POST /app/start/run   (SSE, StartEvent)   ← 준비 8단계, 완전 직렬
POST /app/start/apply (SSE, ApplyEvent)   ← 브라우저, 별도 스트림
POST /lab/notice/control                  ← 사람의 마우스·키보드 (수동 모드)
```

`runStart()` 는 `await stage(...)` 를 여덟 번 줄줄이 부른다(`pipeline.ts:70~169`).
**동시에 두 개가 도는 지점이 하나도 없다.**

`ctx.log` 는 `{ type: "log", text }` 만 보낸다 — **어느 단계의 로그인지 모른다.**
카드마다 로그를 흘리려면 이 필드가 있어야 한다.

---

## 2. 카드 여덟 칸에 무엇을 넣는가

단계는 8개(intake·summarize·judge·research·analyze·prefill·plan·documents)이고
브라우저까지 9개다. 4×2 에 맞추려면 하나를 합치거나 브라우저를 뺀다.

**권고 — 에이전트 기준으로 8칸.** 사용자가 보는 것은 「어느 단계」가 아니라
「어느 에이전트가 일하는가」다.

| 칸  | 에이전트             | 지금 단계               |
| --- | -------------------- | ----------------------- |
| 1   | 입력 정리            | `intake`                |
| 2   | 유효성 검사 (Studio) | `summarize`             |
| 3   | 착수 판정            | `judge`                 |
| 4   | 자료 조사            | `research`              |
| 5   | 정보 분석 (Studio)   | `analyze`               |
| 6   | 데이터               | `prefill` + 사용자 수집 |
| 7   | 계획                 | `plan`                  |
| 8   | 파일                 | `documents`             |

브라우저는 **아래 넓은 한 칸**으로 뺀다. 1280×900 화면을 1/8 칸에 넣으면
아무것도 안 보인다 — 카드 안 썸네일 + 클릭 시 확대로는 「무엇을 하고 있는지」가
안 읽힌다. 그리드 아래 전폭 영역이 맞다.

대안(4×2 를 지키려면): 3번 착수 판정을 2번에 합치고 8번을 브라우저로.
판정은 0.5초에 끝나 카드 하나를 차지할 값어치가 적다.

## 3. 배선 변경 (작다)

### 3.1 로그에 단계를 붙인다

```ts
// pipeline.ts — stage() 가 현재 단계를 알고 있으므로 ctx 를 갈아 끼운다
let current: Stage = "intake";
const ctx: Ctx = { log: (text) => emit({ type: "log", stage: current, text }) };
const stage = async <T>(id: Stage, task: () => Promise<T>) => {
  current = id;
  ...
};
```

`StartEvent` 의 `log` 에 `stage?: Stage` 를 더한다. 기존 화면은 무시하면 되므로
호환이 깨지지 않는다.

### 3.2 카드가 받는 것

카드 하나가 그릴 것은 셋이다 — **상태 · 로그 · 산출물**.

| 카드        | 산출물                 |
| ----------- | ---------------------- |
| 유효성 검사 | 요약 Markdown (접어서) |
| 자료 조사   | 찾은 파일·신청 URL     |
| 정보 분석   | 필드 수 · 준비 문서    |
| 데이터      | 마스터 테이블 채움 n/m |
| 계획        | 단계 목록              |
| 파일        | 만든 파일 이름·크기    |
| 브라우저    | 라이브 화면            |

이미 이벤트가 다 있다(`summary`·`files`·`needs`·`plan`·`artifacts`).
**stage 로 묶어 카드에 꽂기만 하면 된다.**

### 3.3 고정 높이 · 내부 스크롤

```
grid grid-cols-4 grid-rows-2 gap-3
카드: h-56 overflow-hidden flex flex-col
      로그 영역: flex-1 overflow-y-auto
```

새 로그가 오면 아래로 따라붙게 `scrollTop = scrollHeight`. 사용자가 위로
올려 읽는 중이면 따라가지 않는다 — 스크롤이 바닥 근처일 때만 붙인다.

---

## 4. 동시 점등 — 병렬화가 먼저다

지금 실제로 병렬화할 수 있는 곳은 둘이다.

| 묶음                     | 왜 가능한가                                              |
| ------------------------ | -------------------------------------------------------- |
| `research` ∥ `analyze`   | **불가.** analyze 는 research 가 받아 온 파일까지 넣는다 |
| **`plan` ∥ `documents`** | 둘 다 `needs` 확정 뒤에만 필요하고 서로를 안 본다        |
| **`summarize` 파일별**   | 파일 여러 개면 각각 독립. 지금은 `for` 루프로 하나씩     |

`plan ∥ documents` 는 실측으로 21초 + 24초 = 45초가 24초로 준다.
**동시 점등이 화면에 진짜로 생기는 지점이 여기다.**

그 밖에는 직렬이 맞다 — 앞 단계의 산출물이 뒤의 입력이다. 억지로 겹치면
품질이 떨어지고, 화면만 화려해진다.

---

## 5. 티키타카 — 지금은 보여줄 것이 없다

블루프린트 ⑧(브라우저 ↔ 에이전트 상호작용)이 아직 없다. 브라우저는 `facts` 와
계획서를 **한 번 받고** 40스텝을 돌 뿐, 도중에 데이터·파일 에이전트를 부르지
않는다.

지금 되돌아감이 **실제로 일어나는** 곳은 하나뿐이다.

```
documents → recallArtifacts() → 지식베이스 조회
```

즉 파일 카드가 데이터 카드를 부른다. 이것 하나는 진짜라 선으로 그릴 수 있다.

**진짜 티키타카를 만들려면** 브라우저 에이전트에 도구를 두 개 더 준다.

```ts
askUser({ label, why }); // 값이 없다 → 데이터 카드 점등 → 다이얼로그
makeFile({ label, format }); // 서류가 필요하다 → 파일 카드 점등
```

`diagnose` 가 이미 「무엇이 없어서 막혔는지」를 안다. 그 결과를 사람에게
되묻는 대신 도구로 잇는 것이라 구조가 자연스럽다. 이게 생기면 화면에
브라우저 → 데이터 → 브라우저 왕복이 그대로 그려진다.

**작업량**: 도구 2개 + 이벤트 2종 + 데이터 에이전트의 「추가 수집」 경로.
반나절.

## 6. 브라우저 화면

`ApplyEvent.frame` 이 `data:image/jpeg;base64` 를 조작마다 한 장씩 흘린다.
이미 `LiveScreen`(run-view.tsx)이 그걸 그린다 — 그리드 아래 전폭 영역에
그대로 얹으면 된다.

수동 모드(캡챠)에서는 `/lab/notice/live` 로 붙고 `/lab/notice/control` 로
사람이 조작한다. 이미 있다.

---

## 7. 입력 다이얼로그

`NeedsForm` 을 `Dialog` 로 옮긴다. 지금은 페이지 흐름 안에 있어 스크롤하지
않으면 안 보인다 — 지적이 맞다.

주의 하나: **다이얼로그가 뜬 동안에도 진행 이벤트는 계속 온다.** 뒤 카드가
살아 있어야 하므로 모달 배경을 완전히 가리지 않는다(반투명 + 뒤 그리드가
비치게). 그리고 파일 업로드가 다이얼로그 안에서 동작해야 한다 — 지금 구조로
문제없다.

## 8. 중간 개입 — 둘로 갈라야 한다

요청을 뜯으면 두 가지가 섞여 있다.

### 8a. 지시 주입 (가능, 반나절)

```
POST /app/start/steer   { runId, text, mode: "now" | "next" }
```

- **런 레지스트리**: 실행 중인 run 을 id 로 찾는다. `desktop.ts` 의 `sessions`
  Map + `setHold`/`waitWhileHeld` 와 같은 패턴이라 새로운 것이 아니다.
- **`next`(기본)**: 큐에 넣고, `stage()` 가 다음 단계로 넘어가기 직전에 꺼내
  그 단계의 프롬프트에 붙인다. 경계에서만 읽으므로 중간 상태가 깨지지 않는다.
- **`now`**: `AbortController` 로 현재 단계를 끊는다. 단계마다 signal 을 받아야
  하고, LLM 호출(`generateText`)은 `abortSignal` 을 지원한다. 브라우저 조작은
  이미 직렬 사슬이라 그 사이에 끼어들 수 있다.

이 범위에서 지시는 **다음 단계의 입력에 얹히는 것**이지 계획을 바꾸지 않는다.
「주소를 다른 걸로 써줘」·「이 서류는 빼줘」 같은 것은 여기서 해결된다.

### 8b. 재계획 (오케스트레이션을 바꿔야 한다)

「계획 에이전트가 다시 계획하고 나머지를 오케스트레이션한다」 는 지금 구조로
안 된다. **`runStart` 가 여덟 단계를 하드코딩한 순서로 돌린다.** 계획이 실행을
바꾸려면 그 순서가 코드가 아니라 **데이터**여야 한다.

```ts
// 지금
await stage("research", ...); await stage("analyze", ...); ...

// 필요한 모양
let queue: Step[] = plan.steps;
while (queue.length) {
  const step = queue.shift()!;
  const result = await run(step);
  if (steer.pending()) queue = await replan(plan, steer.take(), state);
}
```

여기까지 가면 계획 에이전트가 진짜 오케스트레이터가 된다. 다만 **바꿀 것이
많다** — 각 단계를 이름으로 부를 수 있어야 하고, 상태(마스터 테이블·산출물)를
단계 밖에 두어야 하고, 재계획이 이미 끝난 단계를 다시 부르지 않게 해야 한다.

**하루로는 어렵다.** 8a 로 데모를 하고, 8b 는 블루프린트에 남긴다.

## 9. 권고 순서

앞의 것이 없으면 뒤가 거짓이 되는 순서다.

1. **로그에 `stage` 붙이기** — 모든 카드 표시의 전제. 30분
2. **4×2 그리드 + 브라우저 전폭** — 상태·로그·산출물. 2시간
3. **`plan ∥ documents` 병렬화** — 동시 점등이 여기서 진짜가 된다. 30분
4. **입력 다이얼로그** — 1시간
5. **`askUser`·`makeFile` 도구** — 티키타카가 진짜가 된다. 반나절
6. **8a 지시 주입** — 반나절
7. 8b 재계획 — 데모 뒤

1~~4 는 오늘 안에 된다. 5~~6 은 남은 시간을 보고 정한다.

**하지 말아야 할 것**: 3·5 없이 2 만 만들고 불을 임의로 켜는 것.
움직이는 화면은 만들 수 있지만, 그 화면이 말하는 것이 사실이 아니게 된다.
